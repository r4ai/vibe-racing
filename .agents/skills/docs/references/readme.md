# README の設計基準

リポジトリ直下の `README.md` を新規作成・抜本改訂・更新するときに適用する構成規範である。
OSS 開発者ツール向け README の導線（価値提示 → 概念理解 → 導入 → 設定 → 詳細案内）と、本リポジトリの設計文書（`docs/architecture.md` 等）との責務分離を基礎とする。

## 基本方針

- **対象読者**: 初見の評価者、利用者、開発者・コーディングエージェント（詳細文書への入口として利用）
- **言語**: 日本語（`docs/` 配下の設計文書と統一）
- **目的**: 何のシステムか、基本モデル、主な機能、起動手順、設定方法、関連文書への導線を短時間で把握できる状態にする
- **書かないもの**:
  - 開発・テスト・ビルド手順・UI カタログ運用・プロトコル型生成等の詳細（`docs/development.md` へ分離）
  - 全体の階層設計・依存グラフ・不変条件・全クレート／パッケージの個別一覧（`docs/architecture.md` へ委譲）
  - 未実装機能、ロードマップ、TODO、進捗メモ（現行実装で動く事実のみを記述）
  - 実在しない配布バイナリや未確認コマンドの推測記述

## 章立て構成

以下の章立てを順守する（見出しに連番・`---` 区切りは付けない）。対象外の節は省く。

### `# <プロジェクト名>`

- **バッジ**: 実在し検証可能なもののみ（CI ワークフロー、ライセンス等）をタイトル直下に配置
- **UI ビジュアル**: 実画面スクリーンショットは UI が完成した段階で追加し、未完成の間はバッジと本文中の図で示す
- **リード文（2〜4 文）**: 何のシステムか、構成要素（バックエンド／フロントエンド等）、中核となる利点を 1 文 1 義の短文で記述

### 基本モデル

- 設計の柱を 3〜4 点の構造化箇条書き（太字見出し＋体言止め）で示す
- **概念図（Mermaid）**:
  - `docs/architecture.md` の階層・静的依存図とは視点を分け、利用者のメンタルモデル（人間 ↔ フロントエンド ↔ 常駐デーモン・安全境界 ↔ 外部資源）を 1 枚で図示

### 主な機能

- 長大な散文の段落を避け、利用者が操作・運用する機能のみを関心領域別の小節（例：ツリー運用と対話、モデル・文脈・ローカル計測、権限審査とサンドボックス）へ整理
- 内部実装の詳細は書かず、外部から観測・設定できる振る舞いに絞る

### クイックスタート

- リリースバイナリが無い場合はソースからの起動である旨を冒頭で明記
- **前提環境表**: ツール名・必要バージョン（マニフェストと照合）・OS 別補足を表で提示
- **手順小節（`###`）**: 連番見出しやリスト入れ子を避け、小節ごとに「依存導入 → 認証 → 任意導入（サンドボックス等）→ 起動」の一本道を記述
  - 手元起動で不要な工程（SEA ビルド等）がある場合はその理由を短く注記

### 設定と連携（オプショナル）

- 日常利用で触れる設定画面・設定ファイル（`settings.json` 等）・外部連携（`mcp.json` 等）・ショートカット・利用者向け環境変数に限定して記載
- OS ごとのフォルダパスやショートカット一覧は表で整理
- 開発・デバッグ専用のフラグや環境変数（`PUPPET_TRACE`、`PUPPET_SCRIPT` 等）は `docs/development.md` へ逃がす

### 構成とドキュメント

- **ワークスペース概観表**: `packages/`（Backend）・`crates/`（Frontend）・`vendor/` のような領域単位の要約に留め、個別モジュールの列挙は `docs/architecture.md` に委譲
- **関連文書表**: `docs/architecture.md`、`docs/development.md`、プロトコル仕様、描画・計測詳細、各クレート・パッケージの `README.md` への案内表を配置

### ライセンス

- `Cargo.toml` および `package.json` の定義と一致するライセンス識別子を明記
