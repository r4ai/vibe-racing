# リポジトリドキュメント設計・執筆規範

## 作業手順

### 配置と再編成（肥大化・陳腐化の防止）

局所的な変更や場当たり的な追記で済ませず、文書全体を俯瞰して以下を判断する。

- **記載の要否**: コード・設定ファイル・テストで自明な細部は非記載
- **鮮度の分離**: 進捗・未実装・TODO は構造文書から外し、Issue や別文書へ分離
- **配置ルール**:
  - 全体の設計文書: `docs/`
  - パッケージ／クレート固有の文書: `**/docs/`
  - 概要・導入・利用案内: リポジトリや各パッケージ直下の `README.md`
- **再構成と分割**: 追記の前に全体の整理・統合・不要削除・文書分割を検討

### 文書構造（章立て）の決定

- **型定義済みの種別**: 下表の参照ファイルを先に読み込み、章立てと除外基準に従う
- **型未定義の種別**: 執筆前にベストプラクティスを調査し、読者と目的に合わせて設計

| 文書種別           | 対象                                   | 参照                                                     |
| ------------------ | -------------------------------------- | -------------------------------------------------------- |
| アーキテクチャ文書 | 全体・各パッケージの `architecture.md` | [references/architecture.md](references/architecture.md) |
| README             | リポジトリ直下の `README.md`           | [references/readme.md](references/readme.md)             |

### 実コード照合と検証

- 古い文書や推測で書かず、エントリポイント・依存定義・境界コードを読んで図と記述を検証
- 完了前にリンク実在確認とリポジトリのフォーマッタ（`oxfmt` 等）を実行

## 文章・表現・図表の規範

### 文章構成

- **論理と納得感**: 全体を俯瞰し、前提から結論まで論理の流れが明快で納得感のある構成に整理
- **短文・1 文 1 義**: 1 文を短く保ち、脳のコンテクストを圧迫しない
- **表現の制約**:
  - 過剰な表現を避け、技術的に誠実でニュートラルな表現を使用
  - 「孤島」「聖域」「輪」などの謎の比喩を使わない
  - 「堅牢性」「極小化」「〜に他ならない」等の AI 的装飾を避け、具体的な技術語を使用
- **見出しと区切り**: 見出し連番（`1.` 等）、意味のないサブタイトル、`---` 区切りを入れない

### 箇条書き・表

- **体言止めと構造化**: 箇条書きは体言止めで揃え、長くなる場合は列挙・ネスト・表へ分解
- **表の整形**:
  - セルは極力短く削る
  - 改行が避けられない場合は、日本語の文節として自然な区切りに手動で `<br/>` を挿入
  - レイアウト（列幅・品詞・語尾）を揃えて認知負荷を下げる

### 図解（Mermaid / SVG / HTML）

- **視覚化**: 階層・境界・依存・処理の流れは Mermaid（GitHub Markdown 等）や SVG・HTML で図示
- **視点の分離**: 「抽象・制御の階層」と「静的依存」など異なる視点を 1 枚に混ぜない
- **階層内部の表現**: 多層構造内でさらに階層を持つ層は、ネスト等で内部構造まで図示
- **整列**: 矢印の向き・粒度・ラベル形式を揃え、配線の交差を最小限に抑制
